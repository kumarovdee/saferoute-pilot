# SafeRoute — стенд пилота

SafeRoute проверяет гипотезу для одного канала: перевод физлица новому получателю внутри одного банка. При сочетании сигналов риска подтверждённое поручение остаётся на паузе до решения банка. Клиент может отменить перевод или открыть обращение из приложения.

## Запуск

Распакуйте папку в доступное на запись место. В Windows откройте `start.cmd`. Стенд откроет страницу в браузере. Если браузер не открылся, используйте адрес из окна запуска. Для работы нужен Python 3.10 или новее. Команда для запуска вручную — `python server.py`. Для остановки нажмите Ctrl+C в окне запуска.

Стенд слушает только `127.0.0.1`. По умолчанию данные хранятся во временном файле. Для сохранения истории между запусками используйте `python server.py --db pilot.sqlite`. Проверка кода — `python -m unittest -v`. Для быстрой демонстрации истечения срока выполните `python server.py --hold-seconds 15`. Обычный срок на стенде — пять минут.

## Демонстрация

1. **Рискованный перевод.** Выберите нового получателя с необычной суммой и подтвердите. Повторите подтверждение. Статус остаётся «На паузе», в тестовом реестре нет записи. Отмените.
2. **Законный срочный перевод.** Выберите нового получателя с признаком срочности. Подтвердите и нажмите «Связаться с банком». В панели сотрудника укажите результат учебного разговора и нажмите «Одобрить после проверки». В тестовом реестре появится одна запись.
3. **Теневой режим.** Переключите режим и повторите первый сценарий. Стенд запишет отправку и отдельный сигнал о том, что в активном режиме поручение попало бы на паузу. Поручения, удержанные до переключения, остаются на проверке до решения, отмены или истечения срока.
4. **Истечение срока.** Запустите стенд с коротким сроком и оставьте поручение на паузе. Появится статус истечения, записи об отправке не будет.

В стенде обе роли доступны в одном браузере. Кнопка связи создаёт учебное обращение. Решение сотрудника вводится вручную, отправку представляет запись в SQLite, а признаки риска задаются выбранным сценарием. Суммы, признаки и тексты на экране служат для демонстрации. Казахскую версию и доступность интерфейса нужно проверить с пользователями пилота.

## Интеграция с банком

| Работа | Владелец в банке | Приёмка |
|---|---|---|
| Выбрать точку до передачи поручения платёжному ядру и описать доступные сигналы | Переводы и антифрод | Действующая защита остаётся обязательной. Понятно, какие признаки доступны на момент решения. Для первой версии достаточно сигналов, качество которых можно проверить. |
| Реализовать хранение поручения и выпуск | Платёжная команда | Идентификатор привязан к клиенту, сумме, валюте и получателю. Неоднозначный ответ платёжного ядра сверяется по этому идентификатору. Повторный запрос не создаёт второго списания. Одобрение относится к первоначальным реквизитам. |
| Подключить приложение и очередь | Мобильный банк и контакт-центр | Статус показывает, отправлены ли деньги. Отмена и обращение доступны внутри приложения. Сотрудник аутентифицируется отдельно. Доступ к решению проверяется сервером. |
| Согласовать порядок проверки и сроки | Антифрод, контакт-центр, риски и комплаенс | Есть сценарий разговора, маршрут срочных платежей, порядок на случай перегрузки и недоступности, а также согласованная процедура завершения удержания. Истечение срока само по себе не отправляет перевод. |
| Запустить измерения и управление режимом | Аналитика и эксплуатация | Банк видит возраст очереди, число отмен, истечений, решений и сбоев. Выключение новых удержаний не отправляет автоматически уже удержанные поручения. |

В учебном стенде состояние и запись об отправке находятся в одной транзакции SQLite. В интеграции с отдельным платёжным ядром нужен его ключ идемпотентности и сверка проведённых операций. Для надёжной передачи решения можно хранить задание на выпуск вместе с изменением состояния и передавать его повторно с тем же ключом. После отправки с неизвестным результатом сервис сначала выясняет статус операции в ядре. Таймер в банковском контуре обслуживает фоновый процесс, а право выпустить поручение перепроверяется при каждом изменении состояния. Сценарии сбоя между одобрением и ответом ядра входят в интеграционную приёмку.

## Протокол пилота

1. **Закрытый стенд.** Антифрод банка подбирает случаи, неизвестные разработчикам. Предварительно согласуют правильное действие и способ его проверки. Нужны сценарии под давлением, законные срочные переводы, недоступность оператора, повтор запроса и гонка отмены с одобрением. Пригласите пользователей с разным опытом и проверьте, могут ли они без подсказки объяснить статус и найти отмену.
2. **Теневое наблюдение.** Для каждого подходящего перевода фиксируются решение обычного антифрода, сигнал SafeRoute и результат последующего разбора. Отдельно считают подтверждённые дополнительные случаи, законные срабатывания и обращения в час. Незавершённые разборы отмечают отдельно. Подтверждённые случаи, выделенные теневым алгоритмом, показывают потенциальный охват.
3. **Ограниченный запуск.** Если банк разрешит, используйте сравнимые группы с обычной защитой и с обычной защитой плюс SafeRoute. Фиксируйте группу на уровне клиента, чтобы повторные переводы одного человека не попадали в разные группы. Заранее утвердите объём выборки, окно подтверждения мошенничества и решение на случай нехватки наблюдений.

| Показатель | Как считать |
|---|---|
| Потери клиентов | Подтверждённые потери на 1 000 клиентов, допущенных в пилот, с одинаковым окном последующей проверки в обеих группах. По возможности учесть повторные переводы того же клиента в других каналах. |
| Задержка законных платежей | Медиана и 95-й процентиль от удержания до решения. Отдельно — доля задержанных среди всех законных переводов в охвате и доля законных поручений, которые истекли или были отменены. |
| Нагрузка | Число обращений в час, время обработки, доля обращений старше согласованного срока. |
| Целостность | Дубли, отправка после отмены или истечения, расхождение между статусом в приложении и учётом банка. При нарушении целостности приостановить новые удержания и сверить открытые поручения. |

Порог приемлемой задержки и нагрузку утверждают с владельцами банковских процессов до включения реального удержания. В протоколе отдельно закрепляют, кто может приостановить запуск и кто обрабатывает уже открытые поручения.
